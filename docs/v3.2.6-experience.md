# 红果桌面版 V3.2.6：为更稳定、更流畅的观看体验

2026 年 11 月 17 日 · 升级说明与技术备忘录

### 从“能播放”到“看得更顺畅”

打开一部剧、连续看几集、从推荐进入完整观看、暂停后继续、拖动到想看的位置——这些日常操作，应该尽量自然、连贯。

但在程序内部，一次播放需要经历取源、选择清晰度、读取媒体数据、启动解码、等待首帧，再把画面和声音交给播放器。后台可能还在下载，下一集也在准备。重复的请求、没有及时失效的旧结果、被过早释放的预热对象，以及画面传输中的额外开销，都可能转化为用户看到的等待、重载或中断。

**V3.2.6 把提高用户体验作为重点，围绕稳定和流畅，重新梳理了这些环节。**

稳定，意味着请求失败时能够合理恢复，任务与资源有清楚的生命周期，切换和退出后不会留下混乱的状态。流畅，意味着能提前做的准备尽量提前完成，已经做好的工作尽量复用，减少不必要的重新取源、解码和画面搬运。

下面既是本次升级说明，也是我们对这段优化工作的技术记录。

## 方向一：稳定——减少中断，让后台工作更可靠

### 1. 先把取源与恢复做好，让网络波动得到合理处理

播放稳定的起点，是取得有效片源，并在失效时找到合适的恢复方法。

针对近期匿名 APP 取源失效，我们接入了 Android v5 播放鉴权，将相关请求构造落为本地 Python 实现。最终查询参数、实际发送的 gzip 正文、匿名设备身份与同一时间戳共同参与签名处理，减少请求构造与实际发送内容不一致带来的问题。运行无需外部签名服务、Kotlin 环境或参考程序。

“取不到播放信息”和“取到了地址但媒体读不出来”也分开处理。前者由模型取源层判断，后者由媒体会话检查备用地址与刷新条件。播放、预热、预检和下载使用来源对应的媒体请求头，避免同一地址在不同入口出现相互矛盾的结果。

发生错误时，程序不再把所有情况都当成需要重新注册设备：

- 连接故障和部分服务端 5xx，在预算内尝试已有备用主机。
- 已确认的空响应或缺少模型，才进入有上限的匿名身份恢复流程。
- 401/403、明确业务拒绝和无效模型，按各自错误路径停止或交给对应的恢复处理。
- 429 按服务端 Retry-After 退避，减少连续发送无效请求。

同一媒体会话、同一清晰度最多自动刷新模型一次，并合并同时发生的失败。播放中换地址还要检查分集身份、编码、时长、加密信息、长度和已缓存数据等条件，不能直接把不同资源拼在一起。不能确认一致时，按上限重建播放并恢复位置；手动重试则明确绕过旧模型缓存。

这些工作旨在让失败有原因、恢复有边界。上游持续拒绝或网络确实不可用时，程序仍会报告错误。

### 2. 匿名身份持久化，减少重复注册与不必要的等待

匿名播放也需要设备身份。如果每次启动或每次取源都重新注册，用户要多等一个步骤，也更容易受到注册接口波动的影响。

本版把自动注册的匿名播放身份放入有界设备池，在有效期内跨重启复用。按使用结果调整候选，并临时排除已确认空响应或缺少模型的身份。用户显式配置的播放设备保持优先、只读，不混入自动池。

匿名取流与账号登录继续隔离：播放请求不携带账号 Cookie、Token 或设备令牌，身份池也不保存账号凭据和观看记录。发布包不附带开发机上的真实身份和账号资料。

这项工作的用户价值，是减少每次播放前重复做的准备，让已经有效的身份继续发挥作用。“匿名”在这里指播放与登录凭据隔离，仍会使用取源所需的设备标识。

### 3. 播放调度中心，让播放、预取和下载有序协作

当前播放、下一集预取和下载可能需要同一集的播放信息。各做各的会产生重复请求；把网络等待放进大锁里，又会让缓存、设置等操作一起等待。

我们增加了共享播放模型调度器，按来源、账号上下文和分集编号合并在途任务。同一集可以共享结果，重叠批次只补取尚未登记的分集。状态锁负责短时间的登记和提交，网络请求与结果等待放在锁外，减少慢请求对其他状态操作的影响。

调度遵循明确的取舍：**前台播放/重试、下载、预取按优先级排队；已经开始的有效任务优先连续完成，不因新前台到来就反复取消。** 这样可以减少注册完成却尚未取模就被放弃、后台任务反复重来的情况。新前台有时需要等待当前任务收尾，这是当前策略接受的代价。

每个 Player 同时执行一个模型任务，批次内部仍允许有界的主机/设备竞速：最多四路，约 250 毫秒错开发起，当前目标成功后取消多余请求。我们没有通过无限增加并发来换取表面上的响应速度。

返回结果还要核对来源、账号上下文、代次、修订号和消费者归属。切走的旧分集、刷新前的旧任务不能覆盖新状态；某个等待者超时，也不能误取消其他播放或下载仍需要的共享工作。

这里的“调度中心”负责播放模型请求及其消费者协调。浏览请求和媒体文件传输有自己的管理边界，共同服务连续观看。

### 4. 把会话、设置和退出收尾做完整

稳定也体现在多次切换和长时间使用之后。

GPU 会话从取源、初始化到播放改用同一份登记，修复同一会话被重复计数、导致下一集预加载误报“会话数量超限”的问题。取消、渲染器退出和迟到结果都要核对实际对象，避免旧回调清理新会话。

主窗口与播放器窗口保存设置时，按实际修改的字段合并，嵌套增强选项也采用同样规则，减少一份旧设置把另一窗口的新设置覆盖。需要重启的操作会先等待保存完成。

退出时先发出停止与取消信号，停止下载队列继续领取，再排空工作、释放媒体和认证资源，最后关闭数据库。排队中的登录或扫码任务不能在退出后重新清除取消状态。未完成下载沿用既有恢复机制，已暂停任务保持暂停。

这些改进服务于一个具体目标：用户完成切换或关闭程序后，后台状态也应当跟着正确收尾。

## 方向二：流畅——少一点重复准备，多一点连续观看

### 1. 下一集预热，提前做有用的准备

改善切集等待，既需要提前准备，也需要控制准备工作的成本，不能为了下一集影响当前集。

本版将准备过程分成三层：先取得播放模型和地址，再按需预读媒体数据，最后为最近的下一集建立解码对象并检查真实首帧。点播准备窗口可覆盖后续最多五个不重复、未锁定的候选，但预解码目标只保留紧接着的一集，避免同时启动多个解码器争用资源。

媒体准备按需读取头部、必要索引和续播位置附近的数据；隐藏候选的读取有分段与时间预算，不会自动变成整集后台下载。当前视频先正常出画并稳定播放，再允许下一集预解码进入。首次稳定性检查约在一秒时进行，不满足时约每 400 毫秒复查；慢预检返回后也要重新确认当前状态。

一秒是开始判断能否预解码的时机，不是保证下一集一秒加载完毕。当前播放正在缓冲或跳转时，准备工作仍需遵守准入条件。

### 2. 已准备好的媒体直接交接，减少切集时重来一遍

真正改善连续体验，还需要把预热成果交给正式播放。

我们为准备对象记录播放器归属、一次观看会话、修订号和本地媒体 token，区分“仍在准备”“已经就绪”和“已经接管”。地址、设置、位置及首帧条件匹配时，下一集继续使用已经准备的媒体对象，减少重新赋值地址、重启解码进程和重复等待首帧。

有效对象在暂停和缓冲期间也可以保留，不再仅因前端固定存活时长就被丢弃。地址有效期、候选失效、设置变化、媒体错误和退出仍按各自规则处理，避免为了复用留下过期资源。

Electron GPU 要由 Chromium 实际确认硬件解码和可显示画面；WASM 由媒体对象持有 Worker、音频与帧画布，实际画出首帧才算就绪；FFmpeg Basic 则按匹配的原生预热对象交接。接管时，后续释放责任也跟着转移，防止旧预热清理回调误关正在播放的对象。

用户感受到的目标，是在准备条件满足时减少切集中的重新初始化。没有准备好的片源仍会正常等待。

### 3. 推荐进入完整观看，保留正在看的内容

从推荐点击“完整观看”，如果目标仍是当前分集，就应当尽量延续正在看的画面。

这次让推荐与点播之间保留有效媒体对象、播放位置、暂停状态、音量、静音和倍速，不因为模式切换重新取得当前集播放信息。接近片尾时，约按剩余八秒实际观看时间，将隐藏预热目标转向同剧下一集；进入点播后，再恢复后续候选窗口。

暂停和缓冲不会推进媒体倒计时，拖回片尾窗口之前会恢复相应准备策略。没有可播放的同剧下一集时，不显示下一集倒计时。下一集从零秒准备，避免历史续播位置误进入自然连播。

### 4. FFmpeg beta：尝试降低画面传输成本

流畅不只与网络有关。视频解码、超分、插帧和显示之间的搬运，也会带来时间与资源开销。

**FFmpeg Basic** 保留现有兼容和增强能力：普通原生播放使用随目录 FFmpeg Full，ByteVC2 使用专用组件；已有锐化、修复、去色带、去块、胶片效果和音频增强按能力条件保留。部分 NVIDIA 效果由 FFmpeg 解码后交给 NVEncC VPP 管线处理。

**FFmpeg beta** 采用独立的 NVIDIA GPU 播放管线，当前重点提供插帧、超分、画面尺寸和画面质量。它尝试让画面在 GPU 路径中完成主要处理，再交给 Electron 显示，减少 CPU/GPU 往返：

本地媒体代理 → 独立 FFmpeg 动态库的 CUDA 硬解 → GPU 颜色转换 → 可选 NVIDIA VSR → 可选 NvOFFRUC → D3D11 共享纹理 → Electron sharedTexture → VideoFrame 显示。

这条桥接复用了 Electron 官方接口、FFmpeg、NVEnc 包装组件和 NVIDIA 运行库。本地适配层负责会话、纹理和时序协调。正式视频画面传输不采用 CPU 像素读回、逐帧 HTTP 或像素 ArrayBuffer 上传；GPU 内部仍有颜色转换和纹理复制，因此我们将其描述为减少 CPU/GPU 往返。

beta 的选项独立于 Basic，当前尚未接入的效果继续在 Basic 中使用，已有 Basic 设置不会被 beta 覆盖。

### 5. 共享纹理既要传得快，也要保证画面不会被提前覆盖

把 GPU 画面交给另一个进程，不能只看“已经发送”。消费者可能仍在显示或持有这张画面，生产端过早覆盖同一块纹理，会带来帧内容变化和显示异常。

我们为纹理槽加入租约和代次管理。生产端拿到空闲租约后才能写入，Electron 的 `allReferencesReleased` 确认所有引用释放后，才把槽位交还生产端；seek 和切换会话之后，还要识别旧代次的帧与回调。

当前每个会话使用六个受控槽，每个窗口最多两个 GPU 会话，分别服务当前播放和下一集预热。上限既为连续播放留下空间，也限制帧缓冲和会话资源规模。主动取消、渲染器退出和程序退出统一清理会话与句柄。

在真实 GPU 测试中，我们曾保留六张画面约 700 毫秒不释放，确认帧池停止继续写入，前后像素指纹一致。这项验证直接检查了画面内容，而非只检查收到了几条消息。

显示仍配合现有音频时钟与 xgplayer 控制，保留暂停、拖动、倍速等操作。画面落后时协调追赶和恢复时机，减少连续反复暂停、恢复产生的等待抖动。音频沿用既有链路，不要求声音也在 GPU 上处理。

### 6. 继续修正会打断观看的小问题

**非零起点时间轴。** 部分容器的时间戳从非零位置开始，原来直接使用绝对视频 PTS，可能造成声音已开始而画面仍在等待。现在以容器公共起点统一显示与 seek 换算，同时保留片源本身的音视频相对偏移。测试既核对时间，也核对跳转后的真实画面颜色。

**比例锁定与旋转。** GPU 媒体元素接入现有尺寸和元数据控制，修复已出画却提示尚未加载的问题；超分后使用实际输出尺寸，旋转按正确显示方向处理。

**接近 1080p 的尺寸。** 对小幅边缘尺寸偏差统一采用长短边容差，避免实际片源略大于标称尺寸就被排除。源帧率、编码和硬件条件仍需满足，不通过裁剪或缩小画面来掩盖限制。

**弹幕完整性。** 按官方游标继续读取后续页并去重，后续页失败时允许重新加载，减少首屏有弹幕、后续时间段却因分页遗漏而缺失的情况。

**本地继续观看与提醒。** 最近播放轮播支持最多 20 项；版本联网确认保留 90 天离线宽限，每周期仅在临期三天内和过期时各自动弹窗一次，减少跨天或重启重复提示。验证成功后，临期提醒自动移除。

## 把努力与已经达到的效果讲清楚

本次优化包含设计调整，也包含实测中发现问题后反复修正。我们希望减少等待和中断，同时保留真实的验证边界。

在本机 RTX 3060 Ti 与合成素材上，单独 1080p 24→48 FPS 插帧曾连续采样 65 秒，稳定段约 47.95 FPS，没有记录迟到丢帧。纹理保持、暂停、跳转、非零时间戳、旋转及多种效果组合，也分别做过针对性检查。

高负载组合仍有不足：一组高运动 1080p 素材叠加插帧和 2K VSR 第 2 档，在隔离采样中可能降到约 34～35 FPS，并出现等待。减少搬运没有消除算法本身的计算成本，GPU 平均利用率不到 100% 也不能直接证明能够实时运行。

因此 **FFmpeg beta 仍保留 beta 定位**。当前主要面向 NVIDIA 硬解的 H.264/HEVC SDR，支持 NV12/P010 输入处理、输出 RGBA8；ByteVC2、CPU 软解、完整 HDR 色调映射及部分增强效果不进入新路径。建议先尝试单独插帧或单独超分，再按实际负载选择组合；需要兼容或现有完整增强能力时使用 FFmpeg Basic。

发布前，Node 全量 426 项通过；Python 全量 824 项中 816 项通过、8 项明确跳过，无失败及错误。实际混淆副本还验证了运行时、后端 RPC、合成下载解密、CPU 播放与 seek、扫码输入、自动切集、静帧导出、两次弹窗规则和篡改拒绝，并核对程序包清单、CRC 与远端 SHA256。

这些记录支持已覆盖场景的结论，不能代替全部剧集、所有显卡驱动和长期真实播放验收。四项既有样式断言差异继续保留；部分账号关注仍可能返回 103012，也没有列为本版已修复。

## 技术备忘：我们保留的几项选择

这些取舍会影响后续维护，需要与功能变化一起留下来。

1. **调度优先保证已开始任务的连续性。** 优先级调整待执行顺序，前台不随意抢断有效后台工作。来源或账号变化、显式失效、退出与超时仍有各自的取消边界。
2. **取源、媒体准备与预解码分别管理。** 后续五个候选不等于五个解码器；当前播放稳定和候选有效，是启动下一集预解码的前提。
3. **复用必须带着所有权交接。** 旧请求、旧窗口和旧解码代次的迟到结果，不能覆盖新状态，也不能清理已经转入正式播放的对象。
4. **恢复必须验证一致性。** 模型失败、媒体失败、设备失效和节点波动分别判断；失败恢复有次数和时间上限，播放中的资源替换不能盲目拼接。
5. **GPU 优化同时管理生产与消费。** 共享纹理发送完不等于可以复写，必须等待全部引用释放；缓冲、会话和句柄数量均受约束。
6. **功能通过与性能达标分别记录。** 成功出画、暂停和跳转通过，并不证明所有增强组合都能实时运行；短片段采样也不能替代长期稳定性验证。

[前往 V3.2.6 下载页](https://github.com/cc652464876/hongguo-desktop/releases/tag/v3.2.6)。完整解压到可写目录，更新前关闭旧程序并备份自己的用户数据。程序携带运行组件，无需另外安装 Python、Node.js 或 FFmpeg；FFmpeg beta 仍需支持的 NVIDIA 显卡和驱动。
